## 二、现状架构解析

### 2.1 目录结构

```
博客/
├── index.html          ← 唯一页面:Vue 3 SPA,所有路由/渲染逻辑(约 545 行)
├── css/style.css       ← 全部样式(408 行,17KB,含亮/暗主题与响应式)
├── articles/           ← 内容仓库
│   ├── index.json      ← 文章清单(手动维护,当前 8 篇)
│   └── *.md            ← Markdown 文章,元数据用 `> 日期:` / `> 分类:` 引用块
├── vendor/             ← 本地化三方库(共约 235KB)
│   ├── vue.global.prod.js   (165KB)
│   ├── marked.min.js        (39KB)
│   └── purify.min.js        (29KB)
├── scripts/
│   ├── build-feed.js   ← 生成 rss.xml / sitemap.xml(Node 内置模块,零依赖)
│   └── serve.js        ← 本地预览服务器(端口 8765,含防目录穿越)
├── rss.xml / sitemap.xml   ← 由 build-feed.js 生成
├── 404.html            ← nginx 默认样式,未定制
├── template.html       ← 早期静态模板,死文件(注释已声明不使用)
└── images/favicon.ico
```

### 2.2 运行机制(关键数据流)

```
用户打开 index.html
  └─ Vue 挂载后 scanArticles():
       fetch articles/index.json          ← 获取清单
       └─ Promise.all:逐篇 fetch *.md     ← 全量加载所有文章(注意:不是按需)
            └─ parseMarkdown():正则解析标题 / `> 日期` / `> 分类` / 摘要
  └─ 前端分页:排序后 slice 出当前页(pageSize = 5)
打开文章:hash 路由 #/article/xxx
  └─ 再次 fetch 该 .md → marked.parse → DOMPurify 消毒 → v-html 渲染
  └─ 动态改写 <title> 与 og: meta(SEO 补救措施,但仅对 JS 执行环境有效)
```

### 2.3 技术栈定性

- **运行时渲染 SPA**:所有内容在浏览器端由 JS 生成,服务器只吐一个空壳 HTML + 三个 JS 文件
- **自研 hash 路由**:`#/`、`#/about`、`#/article/xxx`、`#/page/2`
- **自研元数据协议**:`> 日期:YYYY-MM-DD` / `> 分类:xxx`(非标准 front matter)
- **零构建**:没有 package.json、没有打包器、没有构建产物;唯一"构建"是 build-feed.js 生成两个 XML

## 三、与主流静态博客形态的对比

现在常见的静态博客(Hexo / Hugo / Astro / VitePress / Jekyll / Zola)的形态是 **SSG(Static Site Generator)**:

```
Markdown + front matter
        │  构建时(构建机/CI 上跑一次)
        ▼
  每篇文章 → 独立的 article.html(预渲染好的纯静态页)
  列表/标签/归档 → 预渲染的 HTML
        ▼
  部署产物:一堆 HTML,没有"运行时框架"
```

| 对比项 | 本博客(运行时 SPA) | 主流 SSG 博客 |
|---|---|---|
| 文章页面 | 只有 `#/article/xxx` 一个 hash URL,页面靠 JS 现场拼 | 每篇一个独立 `.html`,直接可访问 |
| 搜索引擎收录 | ❌ 内容不在 HTML 源码里;hash URL 不被索引 | ✅ 爬虫直接读到完整内容 |
| 分享链接 | 能打开,但没被收录就搜不到 | 任何平台都能抓取预览 |
| 打开一篇文章 | 下载 235KB JS + 全部文章 md,再渲染 | 只下载那一篇的 HTML(几 KB) |
| 发文章流程 | 写 md + **手动改 index.json** + 跑脚本 | 写 md(带 front matter),构建自动扫描目录 |
| 元数据格式 | 自创的 `> 日期:` 约定 | 标准 YAML front matter,生态通用 |
| 环境要求 | 发布机只需 Node(跑 build-feed.js) | 需要构建环境(但通常 CI 自动完成) |
| 部署 | 传目录即可 | 传构建产物目录即可(同样是传目录) |
| 代码高亮 | 无 | 标配(构建时生成高亮 HTML,零运行时成本) |

**本质差异一句话**:主流静态博客把"渲染"放在**构建时**(一次性、机器做),本博客把"渲染"放在**运行时**(每次、每个访客的浏览器做)。前者换来 SEO + 性能,后者换来"零构建"的简单。

## 四、值得保留的设计(优势清单)

这些是本项目真正的亮点,升级时**应当保留或迁移**:

1. **内容与代码分离干净**:`articles/` 就是纯内容仓库,`.md` 格式可移植到任何工具
2. **XSS 防护链完整**:marked 输出 → DOMPurify 消毒 → 外链自动加 `target="_blank" rel="noopener noreferrer"`(index.html 第 496-513 行)。比大量入门级博客强
3. **三方库本地化**:不依赖 CDN,离线可用、不受 CDN 故障影响
4. **主题防闪烁处理**:`<head>` 内联脚本同步读取 localStorage 偏好,避免暗色模式闪白(第 29-39 行)
5. **交互细节用心**:返回列表恢复页码与滚动位置(第 296-302 行)、分页 URL 可分享(`#/page/2`)、加载失败有明确错误提示
6. **脚本零依赖**:build-feed.js 只用 Node 内置模块,`node scripts/build-feed.js` 一步生成 RSS + sitemap,注释和参数设计(URL 优先级:参数 > 环境变量 > 默认值)都很规范
7. **serve.js 安全意识**:路径拼接前校验 `filePath.startsWith(ROOT)`,防目录穿越
8. **文档完善**:PROJECT_STRUCTURE.md 的"一图看懂"+"日常 workflow"写得比大多数开源项目还好

## 五、问题清单(按严重程度分级)

### 🔴 高优先级(直接影响"被找到")

#### P1-1 搜索引擎收录基本无效 —— 整个站点最核心的问题

- **现象**:首页 HTML 源码里没有文章内容;文章 URL 全部是 `https://.../#/article/xxx` 形式
- **代码依据**:
  - 所有内容经 `scanArticles()` fetch 后由 Vue 渲染(index.html 第 341-375 行),HTML 源码只有空壳
  - `scripts/build-feed.js` 第 136、173 行生成的 RSS/sitemap URL 也是 hash 形式:`${SITE_URL}#/article/${...}`
- **影响**:
  - Google 明确不索引 fragment URL;百度等国内爬虫对 JS 渲染内容收录极差
  - 结果:搜"站名"也许能出首页,搜**任何文章标题或内容**都搜不到——静态博客"记录可检索"的核心价值落空
  - sitemap.xml 形同虚设(提交的 URL 全是 fragment,爬虫不认)
- **修复方向**:见方案 B/C(预渲染出真实路径的 HTML,改用 history 路由或直接静态文件)

#### P1-2 元数据协议非标准,将来迁移成本高

- **现象**:文章元数据用 `> 日期:2026-07-06` / `> 分类:折腾` 这样的引用块约定,而非 YAML front matter
- **影响**:这是**自创协议**,只有本博客的 `parseMarkdown()` 和 `build-feed.js` 认识它。将来想换 Hexo/Astro 等任何工具,8 篇文章需要手工改写;反之,从别处导入文章也麻烦
- **修复方向**:虽然短期可不动,但一旦决定迁移,先花 10 分钟把每篇 md 顶部改成标准 front matter,再动工具(见行动清单 A-1)

### 🟡 中优先级(影响体验与长期维护)

#### P2-1 手动维护 `articles/index.json`,漏登记即"文章消失"

- **现象**:新增文章必须手动把文件名加进数组;加错了顺序、漏加了都不报错,只在页面悄悄不显示
- **影响**:这是最常见的"坑",PROJECT_STRUCTURE.md 里甚至要用 ⚠️ 特别提醒
- **修复方向**:写一个 20 行的 `scripts/sync-index.js`,扫描 `articles/*.md` 按日期自动重写 index.json,并把调用并入 build-feed.js(见行动清单 A-2)

#### P2-2 首屏加载全量文章,文章多了会明显变慢

- **现象**:`scanArticles()` 用 `Promise.all` **一次性 fetch 全部** `.md` 文件(第 356-368 行);分页只分"显示",不分"加载"
- **影响**:现在 8 篇无感;到 100 篇时,首页要发起 100+ 请求;到 500 篇时,移动端几乎不可用。且每次打开都要重新下载
- **修复方向**:轻量做法是列表页只请求一个由 build-feed.js 生成的 `articles/index.json`(预含标题/日期/摘要),点进文章才 fetch 正文——把"运行时扫描"改成"构建时扫描"

#### P2-3 代码块无语法高亮

- **现象**:全项目 grep 不到 highlight/prism/hljs;408 行 CSS 中无代码高亮样式
- **影响**:对"技术/折腾"主题的博客,代码是核心内容,无高亮阅读体验差;而主流 SSG 都是构建时生成高亮,零运行时成本
- **修复方向**:最省事是引入 highlight.js(本地化到 vendor,遵循现有惯例),在 `loadMarkdown` 渲染后调用;或迁移后由 SSG 自动处理

### 🟢 低优先级(锦上添花)

#### P3-1 404 页面是 nginx 默认样式

- 130 字节,只有"404 Not Found / nginx",与站点风格完全脱节。定制一个带站内搜索/返回首页的 404 成本很低

#### P3-2 `template.html` 是死文件

- 注释已声明"实际不使用",但保留在部署目录里,纯属噪音。可删或移入 `docs/` 存档

#### P3-3 无文章归档/标签聚合页

- 分类目前只作为标签展示(`category-tag`),没有"按分类浏览"页面;文章多了以后导航会吃力

#### P3-4 无构建步骤 = 无 CI 可能性

- 现在"部署"完全靠手工上传,没有 CI 可以触发;若走方案 B/C,构建脚本天然可接入 GitHub Actions 等,发布流程可以自动化(写文章 → push → 自动构建部署)

## 六、升级方案对比

### 方案 A:原地优化(不换架构)

保留"运行时 SPA + 零构建"哲学,只修低垂的果子:

| 动作 | 成本 | 收益 |
|---|---|---|
| 写 `scripts/sync-index.js` 自动维护 index.json | 半小时 | 消除"漏登记"坑 |
| build-feed.js 改为生成"含摘要的清单 JSON",列表页只请求清单 | 2-4 小时 | 首屏从"全量 md"降到"一份小 JSON" |
| 引入 highlight.js 本地化 | 半小时 | 代码高亮 |
| 定制 404.html | 15 分钟 | 观感统一 |
| 文章 URL 规范化(hash 改成可被识别的形式) | 无法根治 | ⚠️ **SEO 问题无解** |

- ✅ 适合:完全不在乎被搜索引擎收录、纯自用记录
- ❌ 局限:SEO 短板永远补不上——这是架构层面的天花板,不是补丁能解决的

### 方案 B:加一层"构建时预渲染",保留 Vue 与现有代码

给现有架构加一个 `scripts/build.js`:在 Node 里用同样的 marked + 元数据解析逻辑,把每篇文章**预先渲染成独立 HTML 文件**(如 `posts/xxx.html`),首页/分页也生成静态 HTML;部署产物变成"一堆 HTML + 现有 SPA(作为降级)"。

- ✅ 收益:每篇文章有真实 URL 和完整内容,SEO 立即可被收录;Vue 代码、md 格式、目录结构几乎不动
- ❌ 成本:要自己处理模板拼接、链接生成、导航高亮、分页静态化……**相当于手写一个微型 SSG**,维护成本高于直接用现成的
- 定位:**如果不想离开现有代码,这是通向 SEO 的唯一路**;但不推荐长期持有,见方案 C

### 方案 C:迁移到成熟 SSG(推荐)

内容零改动(或只改元数据格式),换一个构建工具:

| 工具 | 语言/生态 | 适合度 | 备注 |
|---|---|---|---|
| **Astro** | Node(本机已有 v24) | ⭐⭐⭐⭐⭐ | 静态优先、默认零 JS、支持 Vue 组件渐进引入;文章用 `.md` + front matter,天然支持代码高亮/RSS/SEO 插件 |
| VitePress | Node | ⭐⭐⭐⭐ | 文档站风格,和现在"文章+关于"的形态很接近,开箱即美 |
| Hexo | Node | ⭐⭐⭐⭐ | 中文社区最流行、模板多,但插件生态偏老 |
| Hugo | Go(本机未装) | ⭐⭐⭐⭐ | 单二进制、构建极快,但要装 Go 或下载二进制 |

**推荐 Astro 的理由**(针对本项目):
1. **内容直接复用**:`articles/*.md` 拷进去,把 `> 日期:` 两行改成 front matter 即可,正文一字不改
2. **输出形态与现状一致**:产出就是纯静态文件,部署方式不变(还是传目录)
3. **渐进式**:可以先只用 Astro 渲染文章页,保留现有 Vue 组件做交互(主题切换等),不需要一步重写
4. **内置能力补齐所有短板**:代码高亮(Shiki)、RSS、sitemap、分页、tag 聚合页全部是插件/内置功能,不用自己写
5. **SEO 全套**:每篇文章一个真实 URL + 预渲染内容 + 标准 meta,直接被收录

- ❌ 成本:需要接受"构建步骤"这个概念(CI 或本地跑 `npm run build`);要学一点 Astro 语法(约一天上手)

## 七、推荐路线(分阶段)

按"成本从低到高、收益逐步兑现"排,每一步都是独立的、可随时停下的:

```
阶段 0:止血(半天,0 风险,不动架构)
  ├─ A-1 元数据标准化:md 顶部改 front matter(为将来铺路,解析器两种都兼容)
  ├─ A-2 sync-index.js:自动生成 index.json
  ├─ A-3 定制 404.html + 删除/归档 template.html
  └─ A-4 顺手:引入 highlight.js 本地化

阶段 1:定方向(决策点)
  └─ 问自己一个问题:希望别人/搜索引擎能找到你的文章吗?
       ├─ 否 → 停在阶段 0,继续享受零构建(架构本就自洽,无需改)
       └─ 是 → 进入阶段 2

阶段 2:迁移 SSG(1-3 天)
  ├─ B-1 新建 astro 项目,把 articles/ 拷入,front matter 化
  ├─ B-2 实现:文章列表(带分页)、详情、关于、404、RSS、sitemap
  ├─ B-3 换肤:把现有 css/style.css 的设计令牌搬过去,视觉基本不变
  ├─ B-4 保留:主题切换、Vue 交互组件(可选)
  ├─ B-5 部署:构建产物上传,域名不变;旧站保留 301/提示页过渡
  └─ B-6 提交 sitemap:向 Google Search Console / 百度站长提交新站点地图

阶段 3:自动化(半天,可选)
  └─ 接入 GitHub Actions:push 文章 → 自动构建 → 自动部署,从此"只写 md"
```
